# deep-audit: 프로젝트 전수 조사

프로젝트 전체를 기능 단위로 쪼개 **여러 라운드에 걸쳐** 감사한다. 각 라운드는 이전 라운드와 **한 명도 겹치지 않는 새 팀원**으로 구성되며, 새로 발견되는 것이 없을 때까지 반복한다.

역할 분담은 고정이다:

| 역할 | 모델 | 하는 일 |
|------|------|--------|
| **정찰·계획·통합** | Fable 5 (`model: "fable"`) | 코드베이스 전체 훑기, 기능 인벤토리 작성, 팀원별 조사 계획 배분, 라운드 결과 통합·트리아지·수렴 판정 |
| **조사·분석·테스트** | Opus 5 (`model: "opus"`) | 배정받은 기능을 실제로 읽고 돌려보고 검증. 라운드마다 새 인스턴스 |
| **수정 적용** | Opus 5 (`model: "opus"`) | 승인된 항목만 코드에 반영. 분석 팀원과 별개 인스턴스 |

## 핵심 원칙 (반드시 준수)

1. **모델 고정** — 계획·통합은 **반드시** `model: "fable"`, 조사·수정은 **반드시** `model: "opus"`. 비용을 이유로 sonnet/haiku로 내리지 않는다. 모든 서브에이전트 prompt 첫 줄에 식별 문구를 박는다.
   - Fable 호출: `"당신은 Claude Fable 5로 호출된 감사 설계자입니다."`
   - Opus 호출: `"당신은 Claude Opus 5로 호출된 감사관입니다."`
2. **라운드마다 새 팀원** — 이전 라운드 팀원을 `SendMessage`로 이어 쓰지 않는다. 매 라운드 `Agent` 도구로 **새 이름의 새 인스턴스**를 spawn한다. 이름에 라운드 번호를 박아 재사용을 물리적으로 막는다 (`auditor-r2-payments`).
3. **이전 라운드 발견 내용을 새 팀원에게 주지 않는다** — 새 팀원에게 전달하는 것은 "직전 라운드에서 **수정된 파일 경로 목록**"뿐이다. 무엇을 발견했는지는 알려주지 않는다. 선입견 없는 시선이 이 스킬의 존재 이유다. 중복 보고는 Fable이 통합 단계에서 거른다.
4. **조사 팀원은 코드를 고치지 않는다** — 읽기·실행·검증·보고만 한다. 수정은 승인 후 별도 수정 팀원이 한다.
5. **라운드별 승인 게이트** — 각 라운드 통합 보고 후 사용자가 명시적으로 승인한 항목만 수정한다. 승인 없이 다음 라운드로 넘어가지 않는다.
6. **비파괴 테스트만** — 기능 동작 테스트는 읽기 전용·로컬 범위로 한정한다. 상세는 `references/functional-testing.md`의 금지 목록을 따른다.
7. **커밋 금지** — 감사 과정에서 자동 커밋·푸시하지 않는다. 사용자가 요청할 때만.

## 실행 흐름

### Phase 0 — 사전 점검

한 번에 물어보고 넘어간다. 이미 알 수 있는 것은 묻지 않는다.

1. **프로젝트 루트 확정** — `git rev-parse --show-toplevel` 및 `README.md` / `package.json` / `pyproject.toml` 존재 확인. 판단이 서지 않으면 경로를 묻는다.
2. **산출물 디렉터리 생성** — `mkdir -p .deep-audit`. `.gitignore`에 `.deep-audit/`가 없으면 추가할지 사용자에게 한 줄로 묻는다.
3. **실행 환경 파악** — 테스트 명령(`npm test`, `pytest` 등), dev 서버 기동 명령, 필요한 환경변수 유무를 확인한다. 없으면 정적 검증 위주로 진행한다고 알린다.
4. **웹 UI 여부** — 웹 UI가 있으면 dev 서버 URL을 받는다(**서버는 사용자가 직접 띄운다** — 이 스킬이 백그라운드로 기동하지 않는다). 없으면 UI/UX 조사 항목을 계획에서 뺀다.
5. **수렴 파라미터 확인** — 기본값을 제시하고 사용자가 그대로 가도 좋다고 하면 진행한다.
   - 연속 무발견 라운드 = 2 (2라운드 연속 신규 P0/P1 0건이면 종료)
   - 최대 라운드 = 5

### Phase 1 — Fable 정찰 및 조사 계획 수립

`Agent` 도구로 **Fable 5** 1명을 호출한다.

```
Agent({
  name: "recon-planner",
  subagent_type: "general-purpose",
  model: "fable",
  run_in_background: false,
  prompt: <references/recon.md 본문 + Phase 0에서 확보한 환경 정보>
})
```

- `references/recon.md`를 **읽어서 본문을 prompt에 그대로 임베드**한다. 경로만 넘기지 않는다.
- 산출물: `.deep-audit/plan.md` — 기능 인벤토리, 기능별 진입점·핵심 파일·의존 관계, 위험도, 동작 테스트 방법, 그리고 **라운드 1 팀원 배정표**.
- Fable이 배정한 팀원 수를 그대로 쓴다. 기능 규모에 따라 보통 3~6명이며, 상한은 8명이다.
- 계획을 받으면 사용자에게 **기능 인벤토리와 팀 배정만 5~10줄로 요약**해 보여주고 바로 Phase 2로 간다. 여기서 승인을 기다리지 않는다.

### Phase 2 — 라운드 R: Opus 5 팀 병렬 조사

`plan.md`의 배정표대로 Opus 5 팀원을 **한 메시지에서 동시에** spawn한다.

```
Agent({
  name: "auditor-r{R}-{기능슬러그}",
  subagent_type: "general-purpose",
  model: "opus",
  prompt: <references/audit-charter.md 본문
          + references/functional-testing.md 본문
          + 담당 기능 명세(plan.md에서 발췌)
          + 직전 라운드에서 수정된 파일 경로 목록 (R=1이면 생략)>
})
```

각 팀원 프롬프트에 반드시 포함할 것:

- **담당 기능만 본다** — 다른 팀원 담당 영역은 건드리지 않는다. 단, 담당 기능이 호출하는 코드는 경계를 넘어 읽어도 된다.
- **읽기 전용** — 코드 수정 금지. 발견만 보고한다.
- **결과 저장 경로** — `.deep-audit/round-{R}/{에이전트이름}.md`
- **보고 형식** — `references/report-template.md`의 findings 표 형식을 따른다.

라운드 진행 중 `TaskCreate`로 팀원별 작업을 트래킹한다.

### Phase 3 — Fable 통합 및 트리아지

라운드 팀원이 전부 끝나면 **새 Fable 인스턴스** 1명을 호출한다 (Phase 1의 `recon-planner`를 재사용하지 않는다).

```
Agent({
  name: "triage-r{R}",
  subagent_type: "general-purpose",
  model: "fable",
  run_in_background: false,
  prompt: <references/round-protocol.md 본문 + 이번 라운드 결과 파일 경로들 + 누적 처리 이력>
})
```

Fable이 하는 일:

1. `.deep-audit/round-{R}/*.md`를 전부 읽고 중복 병합, 오탐 제거.
2. 이전 라운드에서 이미 처리된 항목과 대조해 **신규 발견만** 추린다.
3. P0/P1/P2 우선순위 부여, 수정 난이도(간단/복잡) 분류.
4. `.deep-audit/round-{R}/SUMMARY.md` 작성 — `references/report-template.md` 구조를 따른다.
5. **수렴 판정** — 이번 라운드 신규 P0/P1 건수를 보고, Phase 0에서 정한 기준에 따라 `계속` / `수렴` 중 하나를 판정해 SUMMARY 상단에 명시.

메인 컨텍스트는 SUMMARY를 읽고 사용자에게 **핵심 5~10줄 + 승인 요청**을 제시한다. 자동으로 수정에 들어가지 않는다.

### Phase 4 — 승인된 항목 수정

사용자가 고를 항목을 지정하면 난이도별로 처리한다.

**간단 (단일 파일, 명백한 1줄~수 줄 수정)**
- 메인 컨텍스트에서 `Edit`로 직접 처리한다.

**복잡 (다중 파일, 리팩터, 동작 변경, 보안 패치)**
- worktree를 파고 새 Opus 5 팀원을 소집한다.
  ```bash
  git worktree add ../worktree-deep-audit-r{R} -b fix/deep-audit-r{R}
  ```
- 수정 팀원은 `name: "fixer-r{R}-{주제}"`, `model: "opus"`, `isolation: "worktree"`로 spawn한다. **조사 팀원과 반드시 다른 인스턴스여야 한다** — 자기가 찾은 걸 자기가 고치면 검증이 성립하지 않는다.
- 수정 후 회귀 확인: 테스트 명령이 있으면 실행하고, 없으면 해당 기능의 동작 테스트를 다시 돌린다. **실패하면 실패했다고 보고한다** — 통과한 척하지 않는다.

수정이 끝나면 변경 파일 경로 목록을 `.deep-audit/round-{R}/CHANGED.md`에 기록한다. 다음 라운드 팀원에게 넘길 유일한 이전 라운드 정보다.

### Phase 5 — 다음 라운드 또는 종료

Phase 3의 수렴 판정과 Phase 0의 파라미터로 결정한다.

- **계속** → R을 1 올리고 Phase 2로 돌아간다. 팀원 이름은 전부 새로 짓는다.
- **수렴** 또는 최대 라운드 도달 → Phase 6.

라운드를 넘어갈 때마다 한 줄로 알린다: `라운드 {R} 종료 — 신규 P0 {n}건 / P1 {m}건, 무발견 연속 {k}회. 라운드 {R+1} 시작합니다.`

### Phase 6 — 최종 보고

`.deep-audit/FINAL-REPORT.md`를 작성한다. 구조는 `references/report-template.md`의 최종 보고서 섹션을 따른다. 포함할 것:

- 라운드별 발견·수정 추이 (수렴 곡선)
- 미해결로 남긴 항목과 그 이유
- 라운드 참여 팀원 명단 (모델 포함) — 재사용이 없었음을 검증 가능하게
- worktree/브랜치가 남아 있으면 머지·정리 여부를 사용자에게 묻는다

`.deep-audit/`는 사용자가 "정리해줘"라고 하기 전까지 남겨 둔다.

## references 사용 규칙

본문은 짧게 유지하고 상세 지시는 `references/`에 분리했다. 서브에이전트를 spawn하기 전 해당 파일을 **읽어서 본문을 prompt에 그대로 임베드**한다. 새 컨텍스트의 에이전트는 한 메시지로 모든 지시를 받아야 길을 잃지 않는다.

| 파일 | 쓰는 곳 |
|------|--------|
| `references/recon.md` | Phase 1 Fable 정찰·계획 |
| `references/audit-charter.md` | Phase 2 Opus 팀원 공통 점검 헌장 (매직넘버·주석·silent fallback·보안·데드코드·UI) |
| `references/functional-testing.md` | Phase 2 기능 동작·기획 적합성 테스트 방법론 |
| `references/round-protocol.md` | Phase 3 Fable 통합·트리아지·수렴 판정 |
| `references/report-template.md` | Phase 3·6 보고서 형식 |

## 자주 빠지기 쉬운 함정

- **모델 헷갈림** — 계획은 Fable, 조사는 Opus다. 반대로 하면 이 스킬의 설계가 무너진다. `Agent` 호출마다 `model` 인자를 명시적으로 확인하라.
- **팀원 재사용** — "이전 라운드 에이전트가 맥락을 아니까 이어 쓰자"는 유혹이 가장 크다. 금지다. 새 시선이 목적이다.
- **이전 발견 내용 유출** — 새 팀원에게 지난 라운드 findings를 요약해 주면 그들은 그 목록을 확인하는 데 시간을 쓰고 새 것을 못 찾는다. 넘기는 건 수정된 파일 경로뿐이다.
- **동작 테스트 생략** — 정적 분석만 하고 "테스트 완료"라고 쓰면 안 된다. 실행할 수 없었으면 **실행하지 못했다고** 보고한다.
- **자동 수정** — 사소해 보여도 승인 없이 고치지 않는다.
- **dev 서버 자동 기동** — 사용자가 띄운다. 백그라운드 프로세스로 환경을 오염시키지 않는다.
- **무한 루프** — 최대 라운드 상한을 반드시 지킨다. 수렴하지 않으면 그 사실 자체를 최종 보고서에 적는다.
