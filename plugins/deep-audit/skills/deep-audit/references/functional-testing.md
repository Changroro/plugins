# 기능 검증 — 기획 적합성 & 실제 동작 (최우선 항목)

이 감사에서 **가장 중요한 부분**이다. 코드가 예쁜지보다, **이 기능이 하기로 한 일을 실제로 하는지**가 먼저다.

두 개의 질문에 각각 답해야 한다. 하나로 뭉뚱그리지 마라.

| 축 | 질문 | 틀렸을 때의 의미 |
|----|------|-----------------|
| **기획 적합성** | 이 기능이 하기로 되어 있는 일이, 지금 구현된 일과 같은가? | 잘 돌아가는 엉뚱한 기능 |
| **실제 동작** | 구현된 대로 진짜 도는가? | 의도는 맞는데 깨진 기능 |

---

## 1. 기획 적합성 검증

### 1-1. 기준선 확보

담당 기능의 **의도**를 코드 밖 근거에서 찾는다. 우선순위:

1. `README.md`의 기능 설명 / 사용 예시
2. `AGENTS.md`, `CLAUDE.md`, `docs/`, PRD, 스펙 문서
3. CLI `--help` 텍스트, API 스키마, 설정 파일 주석
4. 테스트 코드가 단언하는 계약
5. 커밋 메시지·이슈

계획서(`plan.md`)에 적힌 `기획 의도`가 출발점이지만, **그대로 믿지 말고 직접 확인하라.** 계획서를 쓴 사람도 정찰만 했다.

근거를 못 찾았으면 그 사실 자체가 발견 항목이다: `기획 근거 없음 — {기능명}의 의도된 동작을 알 수 있는 문서가 없음`.

### 1-2. 의도 vs 구현 대조

기능의 **관측 가능한 계약**을 항목별로 뽑아 실제 구현과 하나씩 대조한다.

- 입력: 받기로 한 것을 받는가. 문서에 없는 입력을 요구하지는 않는가
- 출력: 돌려주기로 한 형태·단위·정렬·범위가 맞는가
- 부수 효과: 저장·전송·삭제하기로 한 것만 하는가. **하기로 안 한 일을 하지는 않는가**
- 에러 계약: 실패하기로 한 조건에서 실패하는가. 실패해야 할 때 성공하지는 않는가
- 경계 조건: 빈 입력, 최대치, 동시 호출, 재실행(멱등성)

**특히 다음을 의심하라 — 문서와 코드가 어긋나는 전형적 지점:**

- README 예시가 현재 코드에서 그대로 실행되지 않는 경우
- `--help`/스키마에는 있는데 구현이 없는 옵션, 또는 그 반대
- 기본값이 문서와 코드에서 다른 경우
- 이름이 하는 일과 다른 함수·엔드포인트·설정 키

### 1-3. 기능 자체의 타당성

구현과 의도가 일치해도, **그 의도가 이 프로젝트에서 말이 되는지** 한 단계 더 본다.

- 다른 기능과 중복되거나 모순되지 않는가
- 사용자가 실제로 도달할 수 있는 경로에 있는가 (아무도 못 부르는 기능은 데드코드다)
- 실패했을 때 사용자가 무슨 일이 일어났는지 알 수 있는가

과도한 제품 훈수는 금지다. **모순·중복·도달 불가**처럼 객관적으로 지적 가능한 것만 적는다.

## 2. 실제 동작 테스트

정적 분석으로 끝내지 마라. **돌려봐야 한다.**

### 2-1. 실행 경로 확보 (위에서부터 시도)

1. **기존 테스트** — 담당 기능을 덮는 테스트를 찾아 실행한다 (`npm test -- <패턴>`, `pytest <경로>` 등). 통과/실패/스킵을 그대로 기록한다
2. **CLI 직접 호출** — 커맨드가 있으면 `--help`부터 실제 서브커맨드까지 실행한다
3. **HTTP 요청** — 서버가 떠 있으면 `curl`로 정상 케이스 1개, 경계 케이스 1개, 실패 케이스 1개
4. **함수 단위 스크립트** — 위가 모두 불가하면 임시 스크립트를 `.deep-audit/round-{R}/probes/`에 작성해 실행한다. 프로젝트 소스 트리에 파일을 만들지 마라
5. **읽기 전용 추적** — 실행이 전혀 불가하면 진입점부터 데이터 흐름을 손으로 따라간다. 이 경우 결론에 반드시 **`정적 추적만 수행 — 미실행`**을 명시한다

### 2-2. 각 기능마다 최소한 이만큼은 시도한다

- 정상 경로 1개 — 문서의 대표 사용례 그대로
- 경계 1개 — 빈 입력 / 최대치 / 없는 리소스
- 실패 1개 — 잘못된 입력이나 없는 설정. **여기서 조용히 성공하면 silent fallback 발견이다** (`audit-charter.md` C 항목과 교차 보고)

### 2-3. 관찰할 것

- 종료 코드 / HTTP 상태 / 반환값
- stdout·stderr·로그 파일에 남은 내용. **아무것도 안 남는 실패**가 있으면 그 자체를 보고한다
- 생성·변경된 파일, 남은 프로세스, 열린 포트
- 소요 시간 — 눈에 띄게 느리면 기록

### 2-4. 절대 하지 않는 것 (하드 금지)

- 프로덕션·스테이징·공용 원격 리소스에 대한 호출
- 데이터 삭제·마이그레이션·스키마 변경 (`DROP`, `TRUNCATE`, `migrate`, `--force`, `rm -rf`)
- 외부로 나가는 쓰기 — 메일 발송, 메시지 전송, 결제, 게시, 웹훅 발사, 배포
- git 상태 변경 — 커밋, 푸시, 브랜치 전환, stash, reset
- 패키지 전역 설치, 시스템 설정 변경, 서비스 등록
- 소스 트리 파일 수정. 프로브 스크립트는 `.deep-audit/round-{R}/probes/`에만 만든다
- dev 서버·데몬을 새로 기동하는 행위 — 이미 떠 있는 것만 사용한다

**외부로 나가는 부수 효과가 있는 기능은 실행하지 않는다.** 대신 코드 추적으로 검증하고 `외부 부수 효과 — 미실행`으로 표기한 뒤, 그 기능이 안전하게 테스트될 수 없는 구조라는 점(테스트 모드·드라이런 부재)을 발견 항목으로 올린다.

## 3. 보고 형식

발견 항목과 별개로, 담당한 **모든 기능**에 대해 아래 표를 반드시 채운다. 빈칸을 남기지 마라.

```markdown
### 기능 검증 결과

| 기능 | 기획 근거 | 의도 일치 | 실행 방법 | 정상 | 경계 | 실패 | 판정 |
|------|----------|----------|----------|------|------|------|------|
| auth-login | README:42 | 일치 | pytest tests/auth | PASS | PASS | **FAIL** | 실패 시 200 반환 |
| news-send | 근거 없음 | 확인 불가 | 외부 발송 — 미실행 | - | - | - | 정적 추적만 |
```

`판정` 칸에는 결론을 한 줄로 적는다. 문제가 없으면 `이상 없음`, 실행하지 못했으면 그렇게 적는다.

**통과하지 않은 것을 통과했다고 쓰지 마라.** 이 감사의 유일한 실패 조건은 검증하지 않은 것을 검증했다고 보고하는 것이다.
