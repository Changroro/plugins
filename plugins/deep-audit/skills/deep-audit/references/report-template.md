# 보고서 형식

세 가지 형식이 있다. 쓰는 사람이 다르다.

- **A. 감사관 보고서** — Opus 5 감사관이 라운드마다 작성 (`round-{R}/{에이전트이름}.md`)
- **B. 라운드 요약** — Fable 5 트리아지가 작성 (`round-{R}/SUMMARY.md`)
- **C. 최종 보고서** — 메인 컨텍스트가 감사 종료 시 작성 (`FINAL-REPORT.md`)

---

## A. 감사관 보고서

```markdown
# 감사 보고 — {에이전트 이름} (라운드 {R})

- 담당 기능: {id 목록}
- 모델: Claude Opus 5
- 실행 가능했던 테스트: {n}건 / 미실행: {m}건

## 1. 기능 검증 결과

| 기능 | 기획 근거 | 의도 일치 | 실행 방법 | 정상 | 경계 | 실패 | 판정 |
|------|----------|----------|----------|------|------|------|------|
| | | 일치 / 불일치 / 확인 불가 | | PASS/FAIL/- | | | |

담당한 모든 기능이 이 표에 나와야 한다. 빈칸 금지.

## 2. 발견 항목

| # | 등급 | 분류 | 위치 | 내용 | 증상 / 시나리오 | 확신도 |
|---|------|------|------|------|----------------|--------|
| 1 | P0 | 기능불일치 | src/a.ts:42 | | | 확인함 |
| 2 | P1 | silent-fallback | src/b.py:88 | | | 의심 |

- `분류`: 기능불일치 / 기능오동작 / 하드코딩 / 주석 / silent-fallback / 보안 / 데드코드 / UI
- `증상 / 시나리오`: 이게 터지면 무슨 일이 일어나는가. **한 줄 필수**
- `확신도`: `확인함`(실행 또는 코드로 직접 확인) / `의심`(정황만)

## 3. 상세

발견 항목 중 P0·P1만 아래 형식으로 풀어쓴다. P2는 표로 충분하다.

### [#1] {제목}
- **위치**: `path:line`
- **현재 동작**: 
- **기대 동작**: 
- **근거**: (실행 로그 / 코드 인용 / 문서 인용)
- **권장 조치**: 

## 4. 범위 외 발견

담당 범위 밖에서 우연히 본 심각한 것. 없으면 `없음`.

## 5. 확인하지 못한 것

실행 불가였던 경로, 접근 못 한 리소스, 시간이 부족해 훑기만 한 영역. **반드시 채운다.**
```

## B. 라운드 요약 (Fable 트리아지)

```markdown
# 라운드 {R} 요약

## 판정: {계속 | 수렴}

- 신규 P0 {a}건 / P1 {b}건 / 회귀 {c}건 → 합계 N = {a+b+c}
- 무발견 연속: {k}회 (기준 {threshold}회)
- 판정 근거: {한 줄}

## 커버리지

| 항목 | 수치 |
|------|------|
| 보고서 제출 | {n}/{total}명 |
| 검증된 기능 | {n}/{total}개 |
| 실행 테스트 수행 | {n}개 / 미실행 {m}개 |
| 커버리지 구멍 | {목록 또는 없음} |

## 신규·회귀 발견

| # | 등급 | 분류 | 위치 | 내용 | 신뢰도 | 난이도 | 상태 |
|---|------|------|------|------|--------|--------|------|
| 1 | P0 | 기능오동작 | src/a.ts:42 | | ★★★ | 복잡 | 승인 대기 |

- `신뢰도`: ★★★ 복수 감사관 / ★★ 단독 / ★ 의심
- `난이도`: 간단(메인에서 직접 수정) / 복잡(worktree + 팀)

## 재발견 (이전 라운드에서 미승인)

| # | 등급 | 위치 | 내용 | 최초 라운드 |
|---|------|------|------|------------|

## 승인 요청

### 간단 — 즉시 수정 가능
- [ ] #{n} {위치} — {한 줄}

### 복잡 — worktree + 팀 필요
- [ ] #{n} {제목} — 영향 {파일 수}개 파일, {회귀 위험}

## 다음 라운드 배정표 (판정이 `계속`인 경우)

| 팀원 이름 | 담당 | 특별 지시 |
|-----------|------|----------|
| auditor-r{R+1}-{슬러그} | | |

경계를 이전 라운드와 다르게 자른 이유를 한 줄로 적는다.
```

## C. 최종 보고서

```markdown
# Deep Audit 최종 보고 — {프로젝트명} ({YYYY-MM-DD})

## 0. 결론

- 총 {R}개 라운드 수행, 종료 사유: {수렴 | 최대 라운드 도달 | 사용자 중단}
- 발견 {총계}건 → 수정 {n}건 / 미해결 {m}건 / 오탐 제거 {k}건
- **가장 위험한 잔여 항목 3가지**
- 출시 판단: {Go | Conditional | No-Go} — 근거 한 줄

## 1. 라운드별 추이

| 라운드 | 팀원 수 | 신규 P0 | 신규 P1 | P2 | 회귀 | 수정됨 | 판정 |
|--------|---------|---------|---------|-----|------|--------|------|
| 1 | 5 | 3 | 8 | 21 | - | 9 | 계속 |
| 2 | 5 | 0 | 2 | 11 | 1 | 3 | 계속 |
| 3 | 4 | 0 | 0 | 4 | 0 | 0 | 수렴 |

수렴했으면 그 사실을, 안 했으면 **왜 안 했는지**를 한 문단으로 적는다.

## 2. 중점 항목별 정리

### 2.1 기능 검증 (기획 적합성 & 실동작)
전체 기능 {n}개 중 검증 완료 {a}개 / 미실행 {b}개. 불일치로 판정된 기능 목록과 처리 결과.

### 2.2 매직넘버 / 하드코딩
### 2.3 불필요한 주석 / docstring
### 2.4 Silent fallback / silent default
### 2.5 보안
### 2.6 데드코드 / 레거시
### 2.7 UI/UX (해당 시)

각 절에 발견 건수, 수정 건수, 남은 항목을 적는다.

## 3. 미해결 항목

| # | 등급 | 위치 | 내용 | 남긴 이유 |
|---|------|------|------|----------|

`남긴 이유`는 "사용자 반려" / "범위 외" / "별도 이슈로 분리" 중 하나로 명확히 적는다.

## 4. 검증되지 않은 영역

실행 테스트를 끝내 수행하지 못한 기능과 그 이유. **이 절이 비어 있으면 안 된다** — 비었다면 정말로 전부 실행했는지 다시 확인하라.

## 5. 참여 팀원 명단

| 라운드 | 이름 | 모델 | 담당 |
|--------|------|------|------|

라운드 간 이름 중복이 없어야 한다. 중복이 있으면 그것 자체가 프로토콜 위반이다.

## 6. 남은 작업

- worktree / 브랜치: {경로, 머지 여부}
- 후속 제안
```
